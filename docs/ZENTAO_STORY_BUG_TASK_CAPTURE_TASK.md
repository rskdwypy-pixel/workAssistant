# 抓包任务：禅道 18.3「需求拆任务」与「Bug 转任务」（给浏览器抓包 AI 的指令）

> 目的：拿到这两个动作在禅道 18.3 上的**真实请求与响应**，插件才能照着实现。不要凭文档推测，也不要凭经验写字段名。
> 方法沿用之前几轮：Playwright 驱动本机已装的 Google Chrome（`channel: 'chrome'`），用开源版入口 `/zentao/`（企业版 `/biz/` 授权已过期，别用）。登录账号由使用者提供。
> **新界面（zin）要点**：业务内容渲染在 iframe 里；顶层 goto 模块 URL 会走 SPA 路由拿到空 body，要在对应 frame 里操作；保存请求多半是 `X-Requested-With: XMLHttpRequest`。

---

## 0. 准备与约束

- 所有写操作只对**你自己新建的测试数据**做：标题统一带「【插件联调·可删】」前缀。
  - 新建 1 个测试需求（产品用「iOS移动端」，ID 20，指派给自己，评审人选可选的那位；需要时按之前的方法撤销评审变成可编辑 / 可用状态）；
  - 新建 1 个测试 Bug（同一产品，指派给自己）；
  - 用一个**已存在的、使用者自己的执行**做目标执行（先问清楚用哪个；不要新建项目 / 执行）。
- **不要动别人的需求、Bug、任务。**
- 全部做完：删除自己建的任务、Bug、需求，把关联关系恢复（若把测试需求关联进了某个执行，要取消关联），写明最终清理状态。
- 交付物放到仓库 `docs/zentao-capture-<日期>-story-bug-task/`；脚本、原始响应都留。
- **脱敏**：cURL 里的 `cookie` 头一律替换成 `<COOKIE>`；响应里出现密码、token 也替换。（之前几次的 cURL 带着真实 cookie，这次请务必脱敏。）

每个请求给出：**完整 URL、方法、与业务相关的请求头（content-type / x-requested-with / referer）、请求体全部字段（原样）、响应状态码、响应体原文**（HTML 也给）。

## 任务 A：需求拆任务

### A1 需求要满足什么条件才能拆任务
1. 对测试需求，在以下几种状态下分别看界面上有没有「分解任务」「建任务」之类的入口，记录入口的 URL 和是否可点：
   草稿、评审中、激活、变更中、已关闭。（状态怎么切换沿用之前的做法。）
2. 在**激活**状态下，需求要不要先"关联到执行"才能在该执行里建任务？

### A2 把需求关联到执行
3. 找到把需求关联进执行的入口（执行里的"关联需求"，或项目 / 产品里的相应入口），抓：
   - 打开关联页面的请求（URL、响应里的可选需求列表结构）；
   - 提交关联的请求（URL、字段、响应）；
   - 关联后：需求详情里的 `executions`/`projects` 之类字段的变化、需求的 `stage`（阶段）的变化；
   - **取消关联**的请求（清理用）。

### A3 创建关联需求的任务（单个）
4. 在已关联的执行里"建任务"，选这个需求：
   - 打开建任务页的 URL（带需求 ID 的那种，如 `task-create-{执行}-{需求}-…`；URL 每一段的含义写清楚）；
   - 页面里**选了需求后自动带出**的字段（需求描述、预计工时、优先级等）；
   - **保存请求**：URL、全部表单字段原样、响应（成功 / 失败的响应形态、是否带新任务 ID）；
   - 创建后：任务详情里 `story`、`storyTitle`、`storyVersion` 是否正确；需求详情里的 `stage` 变没变、需求页能不能看到这个任务。

### A4 批量创建（拆成多个任务）
5. 使用"批量创建任务"（`task-batchCreate` 或界面上的"批量添加"），一次建 3 个任务（不同类型、不同指派、不同预计工时、其中一个不填预计）：
   - 打开批量页的 URL 与表单结构（字段是数组式？每行有哪些字段？行数怎么控制？）；
   - **保存请求**原样 + 响应；**能否拿到新任务的 ID 们**（响应里有没有，没有的话怎么从列表里找）；
   - 与每个任务关联需求的方式（每行一个需求选择？还是 URL 带的需求 ID？）；
   - 其中一行故意填错（比如标题为空）时，整批是失败还是部分成功？响应怎么说？

### A5 查看需求下已有的任务
6. 需求详情（`story-view-{id}.json?onlybody=yes`）里有没有关联任务的列表（字段名）？字段里有哪些信息（任务 id、名称、状态、负责人、工时）？没有的话，用什么请求能查到"某需求下的所有任务"（例如执行任务列表里按 `story` 过滤）？

### A6 删除任务（清理用）
7. 删除任务的请求（URL、确认方式、响应）。

## 任务 B：Bug 转任务

### B1 入口与预填
1. 在测试 Bug（未确认 / 已确认 / 已解决 / 已关闭 各状态）的详情里，看有没有「转任务」（`toTask`）入口：各状态下是否可用，入口 URL。
2. 点「转任务」打开的页面：URL 每一段的含义；页面上**自动预填**了哪些字段（标题、描述、优先级、指派人、预计、截止…）以及预填的规则（描述里是不是带了 Bug 的重现步骤？标题有没有前缀？）。
3. 页面上能选的**执行**有哪些规则？（Bug 所属产品必须与执行所属项目匹配吗？不匹配的执行能不能选？）

### B2 保存
4. **保存请求**：URL、全部表单字段原样（特别是关联 Bug 的字段名，如 `fromBug`）、响应形态、是否带新任务 ID。

### B3 转完之后
5. Bug 详情（`bug-view-{id}.json?onlybody=yes`）里：`toTask` 的值、`status`、`assignedTo`、`resolution`、`activatedCount` 是否变化；界面上显示什么文案（如"已转任务"）。
6. 任务详情里：`fromBug` 是否正确；描述里有没有自动附上 Bug 信息。
7. 同一个 Bug **再次**点「转任务」会怎样（拒绝？能再建一个？）。
8. 转出的任务被删除后，Bug 的 `toTask` 会不会回到 0。

## 任务 C：通用信息

1. **执行列表**：能不能用一个请求拿到"当前账号可见的执行及其所属项目 / 产品"（插件已有执行列表，这里主要确认**执行与产品**的对应关系从哪里取）。
2. 任务类型（`type`）的全部取值与中文名（设计 / 开发 / 测试 / 研究 / 讨论 / 界面 / 其它 …），以及 `pri` 的取值范围。
3. 新建任务时 `assignedTo[]` 的格式（多人任务 / 单人）、`estStarted` / `deadline` 的格式（有没有"不能早于执行开始日期"之类的校验，错误提示原文）。
