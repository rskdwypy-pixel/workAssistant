# 「补」——调试模式下的工时自动补填 PRD

> 状态：**P0（日补）、P1（月补）已实现**（2026-10-23）。P2（调试页配置项等）未做。
> 已确认的决定：今天不出现「补」；候选池只用「进行中」的任务；预览确认始终保留；工作内容不带「（补）」标记。
> 实现：后端 `src/services/autofillService.js` + `routes/autofill.js`；前端 `extension/autofill.js`（弹窗）+ `reports.js`（调试模式下的按钮）。
> 前置：工作日历 P0/P1/P2 已完成（工时以禅道为准，可新增 / 补填过去 / 修改 / 删除，见 `STATS-PRD.md`）。

---

## 1. 背景与目标

**场景**：漏填了几天工时，要一条条点进去补，既慢又枯燥。想要：在**调试模式**下，工作日历的缺工时的日子上有个「补」按钮，一点就用**真实存在的任务**把当天补到标准工时，工作内容由 AI 结合任务本身来写；月份层面还要有「一键补本月」。

**目标**

1. 一天、一个月的缺口，几次点击补齐。
2. 补进去的每一条都**挂在真实任务上**，内容贴合该任务，且**不改变任务本身的状态**（不会把任务意外开始、暂停、完成）。
3. 写入的是禅道里的**正式工时**，所以必须**先预览、能改、能撤销**。

**非目标**：不补周末 / 未来；不代别人补；不动已有的工时记录；不是日常入口（只在调试模式下出现）。

---

## 2. 入口与可见性

| 入口 | 位置 | 出现条件 |
|---|---|---|
| **日补** | 日历格子右上角的小「补」按钮 | 调试模式开 **且** 该日是**过去的工作日** **且** 当天工时 < 标准工时（含 0） |
| **月补** | 月份导航里「本月」按钮后面的「补」按钮 | 调试模式开 **且** 本月有至少一个满足上面条件的日子；没有缺口时置灰并提示"本月没有缺工时的日子" |

- 调试模式关闭时，两个按钮都不渲染（不是隐藏样式，而是不生成 DOM）。
- 打开 / 关闭调试开关后，日历立刻重绘，不用刷新页面。
- 后端接口本身不依赖前端开关（插件的后端只对插件开放），但**所有写入只能走「预览 → 确认」两步**，没有"一步直写"的接口。

## 3. 交互流程

### 3.1 日补

```
点格子上的「补」
   ↓ 生成方案（0.5~几秒，AI 写内容）
┌ 补填预览 · 10月22日 周四 ──────────────── 已填 1h / 8h · 要补 7h ┐
│ 1) [任务 ▾ 接口联调]                 [3 h]  [内容……可编辑]   ✕    │
│ 2) [任务 ▾ 首页待办聚合]             [2.5h] [内容……可编辑]   ✕    │
│ 3) [任务 ▾ 禅道同步插件功能开发]     [1.5h] [内容……可编辑]   ✕    │
│ 合计 7h（还差 0h）           [换一批任务] [重写内容]             │
│                                         [取消]  [确认写入]       │
└──────────────────────────────────────────────────────────────────┘
确认 → 逐条写入 → 完成提示「已补 7h（3 条）· 撤销」→ 日历格子刷新
```

- **每条都可改**：换任务（下拉是同一个候选池）、改小时（0.5 步长）、改内容、删除这一条；合计实时显示"还差 / 超出"。
- **换一批任务**：重新随机抽（保留已手改的条目可选，默认全部重抽）；**重写内容**：只重新让 AI 写内容，任务和小时不变。
- 合计 ≠ 缺口也允许写入（比如你只想补一部分），但超过标准工时会提示"超出 X 小时"。

### 3.2 月补

```
点月份导航里的「补」
   ↓ 为本月缺工时的每一天生成方案（逐天并行，进度条）
┌ 补填预览 · 2026年10月 ─────────── 共 11 天 · 要补 78h · 共 31 条 ┐
│ ☑ 10-08 周四  已填 4h → 补 4h   接口联调 2h｜首页待办 2h   ▾展开  │
│ ☑ 10-09 周五  已填 0h → 补 8h   …                         ▾展开  │
│ ☐ 10-12 …（可以取消勾选某一天）                                   │
│ 跳过的日子：10-01~10-07（国庆）没有可用任务 …                      │
│                                  [取消]  [确认写入所选的 N 天]    │
└──────────────────────────────────────────────────────────────────┘
确认 → 后台逐条写入（进度条 23/31）→ 完成汇总：成功 / 失败（可重试）→ 「撤销本次补填」
```

- 展开某一天可以像日补一样逐条修改。
- 同一个任务在一个月里被反复抽到时，方案会**限制频次**（见 §4.4），避免整月都是同一个任务。
- 写入是**后台任务**：关掉预览窗也继续，进度在日历页头显示；任何时候可以停止（已写入的保留，可撤销）。

### 3.3 撤销

- 每一批补填都有一条**补填记录**（批次号、时间、写入了哪几条工时的 id）。
- 完成提示和调试页的"补填记录"列表里都有「撤销」：逐条删除这批写入的工时；**只删仍然存在、且内容未被改过的**，其它的跳过并说明。
- 撤销本身也写记录。

## 4. 选任务：怎么保证是"真实任务"

### 4.1 候选池：当天已存在的、能安全补记的所有任务

> **2026-10-23 修订**：最初只用"现在进行中"的任务，结果补历史时池子几乎是空的——用户指派给他的 180 个任务里 171 个已经完成，进行中的只有 3 个，而且都是 10 月中旬才创建的。补历史最需要的恰恰是"当时在做、现在已完成"的任务。用真实禅道做了实验，确认**在已完成的任务上补记工时是允许的，任务状态、完成日期都不变，剩余仍为 0**，于是放宽如下。

数据来自"指派给我"和"我完成的"任务（含创建 / 预计开始 / 实际开始 / 完成日期 / 预计 / 消耗 / 剩余 / 状态）。先要求**当天已存在**（创建、预计开始、实际开始都不晚于当天），再按状态：

| 任务现在的状态 | 能不能用 | 条件 |
|---|---|---|
| 进行中 | ✅ | 剩余工时 > 0 |
| 已完成 | ✅ | 不限完成日。当天还没完成的最贴近事实；更早就完成的权重 ×0.4（能选，但不优先）——2026-10-24 放宽，原因：某些天候选只剩一个，应从全部任务里挑 |
| 未开始 / 暂停 | ❌ | 实验证实：在未开始的任务上记工时，禅道会自动开始它，并把"实际开始"设成**现在**，删掉工时也回不去 |
| 已关闭 / 已取消 | ❌ | 没验证过 |

写入时：进行中的任务剩余沿用当前值；已完成的任务传 0 并确认完成（它本来就完成了，禅道忽略剩余）。预览里"已完成"的任务在下拉里有标记，并有一条说明。

### 4.2 剩余工时

进行中的任务：写入时 `left` 一律取**任务当前的剩余值**，不改变任务剩余、不触发完成（已用真实写入验证过）。已完成的任务：传 0 并确认完成，任务保持已完成（已用真实写入验证过）。

### 4.3 权重（让选择更像"真的做过"）

在候选池里按权重随机，权重来自你自己在禅道里的真实痕迹：

| 因素 | 影响 |
|---|---|
| 当天前后 3 天里你在这个任务上**已有工时** | 加权（工作有连续性） |
| 这个任务的**截止日期**在当天之后不远 | 加权（临近截止的任务更可能在做） |
| 任务的**最后编辑时间**接近当天 | 加权 |
| 与当天**已有工时记录同一个执行（迭代）** | 加权（同一时期通常在同一个迭代里） |
| 这个任务本月已被补填的次数多 | 降权（见 §4.4） |
| 任务预计工时已用完（消耗 ≥ 预计，预计 > 0） | 降权 |

### 4.3.5 总量：不少于标准工时，允许小幅加班（2026-10-23 新增）

每天要补的量 = **补到标准工时所需的量（向上取到 0.5，所以补完一定 ≥ 标准工时）+ 随机的小幅加班**。加班 0.5 步长，范围 0 ~ 上限（默认 2h，调试页可调，0 = 不加班），越小越常见（上限 2h 时约：不加班 33%、0.5h 27%、1h 20%、1.5h 13%、2h 7%），这样每天的总工时不是整齐的 8，而是 8 / 8.5 / 9 / 9.5 / 10 之间变化。已经 ≥ 标准工时的日子不动（只加不减）。预览里写明"补 9h（含加班 1h）"，每条仍可改。

### 4.4 数量与分配

- 每天抽 **1~3 个任务**（缺口越大越多：≤2h 取 1 个，≤5h 取 1~2 个，>5h 取 2~3 个）。
- 小时按 0.5 步长，**单条最少 1h、最多 4h**，总和恰好等于缺口（缺口不是 0.5 的倍数时补到最近的 0.5）。
- 同一个任务**同一天只出现一次**。
- 月补时同一任务在整个月里最多被抽 **8 天**（可调），避免整月只有一个任务。
- 方案由**随机种子**决定（种子 = 日期 + 账号 + 点击次数）：同一次生成可复现，「换一批」换种子。

### 4.5 候选池为空时

当天池里没有任务 → 该天标记"跳过：没有当天已存在的进行中任务"，在预览里列出原因，**不会硬凑**。

## 5. 工作内容怎么写（AI）

### 5.1 输入

对每一条（任务 × 当天）把这些交给 AI：

- 任务名、任务描述（`task-view`）、所属执行 / 项目、任务当前进度与状态；
- **你在这个任务上的历史工时内容**（最近 5 条，用来学习你的口吻、详略、用词）；
- 你在其它任务上最近的几条内容（学习整体写法）；
- 这一天的其它条目（避免两条写得雷同）；
- 小时数（时间长的写得具体些，时间短的一两句）。

### 5.2 输出约束

- 中文，**1~2 句**，长度与你自己平时的内容相近；
- 只描述**任务范围内**合理的工作（"联调接口""梳理需求""修复…"这类），**不编造**具体数字、缺陷编号、人名、版本号、上线结论；
- **不声称完成**（不写"已完成/上线/验收通过"），避免与任务状态矛盾；
- 同一天、同一批里不重复措辞。

### 5.3 降级

AI 未配置或失败时：从该任务**你自己的历史内容**里挑一条做轻度改写；没有历史就用"推进「任务名」相关工作"；预览里标明"本条为模板内容"，并提示去配置 AI。

### 5.4 成本与速度

按天批量调用（一天一次请求写完当天所有条目）；月补并行 3 路；单次失败不影响其它天。

## 6. 写入与一致性

- 复用现有 `addEffort`（已有校验、回读核对、缓存失效），**逐条串行**写入，条间间隔约 300ms，避免冲击禅道。
- 写入前**重新读取当天最新工时**：如果已经被补满（比如另一处刚填过），该日整体跳过，防止重复补。
- 单条失败：记录原因，继续下一条；整批结束后汇总，失败项可点"重试失败项"。
- 遇到登录失效：立即停止并提示，已写入的保留。
- 单次最多 **31 天 / 100 条**，超过拒绝并提示分批。
- 写入后日历、抽屉、待办的"工时待补"自动刷新（沿用现有刷新机制）。

## 7. 数据与接口（草案）

| 接口 | 说明 |
|---|---|
| `POST /api/efforts/autofill/plan` | `{ dates:[…] \| month, seed? }` → `{ planId, days:[{date, existing, gap, entries:[{taskId, taskName, execName, hours, work, source:'ai'\|'template'}]}], skipped:[{date, reason}], aiUsed }`。**只生成方案，不写任何东西。** |
| `POST /api/efforts/autofill/rewrite` | 重写某条（或某天）的内容 |
| `POST /api/efforts/autofill/execute` | `{ planId, days:[{date, entries:[…编辑后的…]}] }` → `{ jobId }`；后端校验方案来自本机生成、条目符合 §4 的硬条件（任务在池里、不超过当天缺口上限）后开始后台写入 |
| `GET /api/efforts/autofill/jobs/:id` | 进度：`{ total, done, failed:[…], state }` |
| `POST /api/efforts/autofill/undo` | `{ batchId }` → 逐条删除这批写入的工时 |
| `GET /api/efforts/autofill/log` | 补填记录列表 |

- 补填记录存后端 `data/autofill-log.json`（批次、时间、条目 `{effortId, taskId, date, hours, work}`、撤销状态）。**前端不存任何东西**（延续"数据以后端 / 禅道为准"）。
- 候选池、权重、AI 提示词都在后端；前端只负责展示和编辑方案。

## 8. 调试页里的配置（P2）

调试模式开关下面多一块"工时补填"设置（存后端设置，走 `GET/POST /api/config`）：

- 每天任务数范围（默认 1~3）、单条最少 / 最多小时（默认 1 / 4）；
- 同一任务单月最多被抽的天数（默认 8）；
- 内容提示词（可改，有默认）；
- 候选池是否包含"暂停"的任务（默认不含）。

## 9. 风险与边界

| 风险 | 对策 |
|---|---|
| 写入的是**正式工时**，写错 / 重复不好收拾 | 必须预览确认；写入前重读当天最新工时防重复；每批有补填记录，一键撤销 |
| 在不该动的任务上记工时，改变任务状态 | 候选池只含"进行中且当天已存在且剩余 > 0"的任务；剩余沿用不改；不碰未开始 / 暂停 / 已结束的任务 |
| AI 编出不存在的细节 | 提示词禁止编造数字 / 编号 / 完成结论；内容在预览里可逐条修改；AI 不可用时降级为模板并标注 |
| 整月都是同一个任务，显得不自然 | 月内单任务频次上限 + 权重降权 |
| 调试开关被误开 | 开关本身在设置里，开启时已有"调试模式已开启"提示；按钮只在日历里出现，且所有写入都要二次确认 |
| 使用边界 | 这个功能写进的是团队的正式工时记录。设计上它帮你把**确实做过但漏填**的时间，按你真实有的任务补进去——预览和补填记录就是为了让每一条你都看得到、改得了、撤得回。 |

## 10. 分阶段

| 阶段 | 内容 |
|---|---|
| **P0** | 今天高亮（已完成）；调试开关联动；**日补**：候选池 + 权重 + 分配 + AI 写内容（含降级）+ 预览编辑 + 写入 + 补填记录 + 撤销 |
| **P1** | **月补**：批量生成、进度、后台写入、失败重试、停止；月内频次限制 |
| **P2** | 调试页配置项；内容风格学习增强；候选池"未开始 / 暂停"任务的可选支持（需先验证禅道在这些状态下记工时的副作用）；周末 / 调休日选项 |

## 11. 验收标准（P0）

1. 调试模式关闭：日历里没有任何「补」按钮；打开后立即出现，仅出现在"过去的工作日且工时 < 标准"的格子上。
2. 点「补」：预览里的所有任务都满足 §4.1 的三个硬条件；合计等于缺口（按 0.5 取整）；每天 1~3 条；同一任务同一天不重复。
3. 预览可改任务 / 小时 / 内容、可删条目、可「换一批」「重写内容」；合计实时更新。
4. 确认后禅道里的记录与预览一致（日期、任务、小时、内容），任务的剩余、状态不变。
5. AI 不可用时仍能生成方案，条目标注"模板内容"。
6. 撤销后禅道里这批记录消失，其它工时不受影响；被手工改过的跳过并提示。
7. 同一天被别处补满后再点确认：该天跳过，不重复写入。

## 12. 已确认（2026-10-23）

1. **今天**不出现「补」（今天还没过完）。
2. **候选池**最初只用"进行中"的任务；后来发现补历史几乎没有可用任务，已放宽为"那一天正在做的任务"（进行中，加上当天还没完成、现在已完成的）；"未开始 / 暂停"仍不用。
3. **预览确认**始终保留，不提供"跳过预览直接写入"。
4. 补填的工作内容**不带**"（补）"标记（补填记录存在后端，可查可撤销）。
