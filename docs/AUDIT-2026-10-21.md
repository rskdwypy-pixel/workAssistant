## A. 同步慢 / 同步不全

- [x] **A1 我的任务只同步第一页（已实测）**
  `src/services/zentaoService.js:483` 只请求 `my-task.json`，禅道返回 `recTotal:193, recPerPage:20, pageTotal:10`，每次最多 20 条。
  修复：请求 `my-task-assignedTo-0-id_desc-<recTotal>-<recPerPage>-<pageID>.json` 逐页拉取，或一次性设大 recPerPage。

- [x] **A2 「同步执行」恒为 0 条（已实测）**
  `src/services/zentaoService.js:887` 正则匹配结果末尾多带引号，`JSON.parse` 报 `Unexpected non-whitespace character after JSON at position 108425`，错误被吞掉，返回 `[]`。
  修复：改为捕获组 `/<script>\s*data\s*=\s*"((?:\\[^]|[^\\"])*)"/`，再用 `m[1]` 解析（已验证可解析出 52 个执行）；失败时抛错，不要返回空数组。

- [x] **A3 每 2 分钟一次无效登录（日志里有 350 次）**
  `extension/newtab.js:6154/6219/6273`：保活检查的是浏览器里的 `zentaosid` cookie，后端直连后这个 cookie 永远不存在 → 每 2 分钟 `POST /api/zentao/login` → 后端完整登录一次，而且**不更新**后端的会话缓存。
  修复：删除 ZentaoBrowserClient 的登录与保活（见 D3）；`/api/zentao/login` 改为刷新 `getZentaoCookies` 的缓存，且不返回 cookie。

- [x] **A4 请求禅道没有超时**
  `zentaoService.js:17` 全局 fetch 包装没有 `signal`。断网 / 没连 VPN 时，连接阶段要等约 10 秒；对方响应慢时最长等 300 秒。
  修复：统一加 `AbortSignal.timeout(10000)`；登录时多个并发请求合并成一个 Promise。

- [x] **A5 后端会话缓存时间写死 1 小时，不检查会话是否还有效**
  `zentaoService.js:135`。禅道会话提前过期时，请求直接失败。
  修复：检测到返回的是登录页 / 跳转响应时，清掉缓存，重新登录后重试一次。

- [x] **A6 插件拉起后端时至少白等 6 秒**（详见 C4）

## C. 插件拉起后端 / 开机自启

- [x] **C1 任何网页都能关闭后端或关闭开机自启**
  `src/routes/admin.js:17` 的 `isLocalRequest` 只检查 IP，但浏览器网页的请求同样来自 127.0.0.1。再加上 CORS 是 `*`：
  - `/api/admin/shutdown`：普通 POST 不需要预检，可直接关掉后端；
  - `/api/admin/autostart {enabled:false}`：可关闭开机自启并删除 plist。
  修复：校验 `Origin`，只允许 `chrome-extension://<扩展ID>`，并要求本地 token（和 E1 一起修）。

- [x] **C2 「停止」或「重启」后，后端变成跟浏览器同生共死**
  `admin.js:146` 停止时会对 launchd 的任务执行 `bootout`（卸载到下次登录）；之后「启动」走 `backend-launcher.sh`，浏览器退出时启动脚本会把后端一起结束掉（`backend-launcher.sh:85`）→ 21:00 日报 / 周报静默丢失，界面上开机自启仍显示「已开启」。
  修复：停止 = 进程以 0 退出（KeepAlive.SuccessfulExit=false 不会重启）；启动时如果装了 LaunchAgent，优先 `launchctl kickstart gui/<uid>/com.workassistant.backend`。

- [x] **C3 shutdown 会 bootout 自己**
  后端是 launchd 启动的时候，`bootout` 会立刻给它发 SIGTERM，`index.js` 直接 `exit(0)`，回复来不及发出。违反了 install-launchagent.sh 注释里「绝不 bootout 自己的 job」这条规矩。

- [x] **C4 启动脚本从不发送 ready 消息 → 每次拉起都等满 6 秒**
  `background.js:71` 等待 `{type:'ready'}`；`backend-launcher.sh` 从来没往标准输出写过任何消息。
  修复：后端就绪后，按 Native Messaging 格式（4 字节小端长度 + JSON）写一条 ready。

- [x] **C5 后台被唤醒时并发启动 + 启动脚本常驻不退出**
  `background.js:874` 在后台被唤醒时直接调用 `bootstrapBackend()`，和 `onStartup` 的那次并发执行，于是 connectNative 两次（实测 Helium 下挂着 2 个启动脚本，已存在 1 天 9 小时）。发现端口已被占用、复用现有后端的那个启动脚本会一直阻塞在 `cat` 上。
  修复：用一个共享的 Promise 合并启动；复用现有后端时，启动脚本直接退出。

- [x] **C6 磁盘上的 plist 与 launchd 已加载的配置不一致**
  launchd 实际运行的是 `/usr/local/bin/node` v22.20；磁盘上 plist 写的是 `~/.nvm/versions/node/v20.19.5/bin/node`。原因是 `install-launchagent.sh:113` 在任务已加载时不重新加载。另外 nvm 的路径很脆弱（卸载这个版本后后端会启动失败，launchd 按约 10 秒一次的节流不停重启）；`jsdom@30` 要求 Node 22 以上。
  修复：重写 plist 后执行 bootout + bootstrap（或 `kickstart -k`）；node 优先用固定路径。

- [x] **C7 `WORKASSISTANT_LAUNCHED_BY` 从未设置**：`admin.js:34` 判断启动方式会出错（插件拉起的会显示成 manual 或 launchd）。

- [x] **C8 端口被任意程序占用时，后端都会以 0 退出**（`index.js` 的 EADDRINUSE 分支），launchd 不会重启；启动脚本的端口探测也只看端口有没有被占用。
  修复：先探测 `/health`，确认占用端口的是本项目，否则以非 0 退出并给出提示。

- [x] **C9 `uninstall-launchagent.sh` 默认不卸载任务**，本次登录期间任务仍处于加载状态（崩溃后是否还会被拉起，未实测）。

- [x] **C10 日志 `/tmp/workassistant-backend.log` 权限 644、没有轮转**，内容里有 Bug 和任务的完整 JSON；`/tmp` 会被系统定期清理。
  修复：改到 `~/Library/Logs/workassistant/`，权限 600，并做简单的大小轮转；去掉整条数据的 dump。

- [x] **C11 Firefox 宿主文件的 `allowed_extensions: []` 是空的**，必然连接失败，脚本却显示「已注册」。
- [x] **C12 plist 用 heredoc 拼接，路径没有做 XML 转义**（路径含 `&` 或 `<` 时生成的 plist 会损坏）。

## H. 附件功能开发中发现（2026-10-21 第三轮）

- [x] **H4 解决 Bug 失败只提示「未知错误」**：读的是 reason，后端返回 message。

- [x] **H7 上传成功的附件仍显示「待上传」**：推送到禅道是异步的，卡片列表只在添加时刷新一次，推送完成后角标停留在旧状态；且已同步禅道的 pending 实为排队推送，却显示「待上传」。修复：新增推送观察器（推送结束后刷新列表）；已同步禅道的 pending 显示「上传中」，未同步才显示「待上传」。
